# Nine offline ROS CLI operations

Validated on board A with all nine selected operations passing. The existing
98-case template remains unchanged. These commands require local
ROS Python/native dependencies but no Node, Context initialization, executor,
DDS peer, broker daemon or network discovery. `generate_policy` is excluded:
it needs a complete live fixture. Security utilities do load rclpy for namespace
validation and the RMW identifier; this does not create a Context.

From ros2 in Git Bash, use a fresh run ID after reviewing the frozen inputs:

```sh
MDDS_RUN_ID=cli_offline_20260906_03 bash scripts/run_mdds_cli_offline.sh
```

A is the exact first board in the unchanged standard. The existing owned-process
helper owns the activity lock, supervisor and child. The existing metadata
supervisor waits through actual Python teardown; the existing hash-transfer and
bounded flat JSON/log archive extraction are reused. Default wait is 1200s.
The board gets the installed ohos_dsoftbus profile. Every actual CLI is invoked
through the installed ros2cli entry point in its own subprocess and its real
return code is recorded, never an HDC shell return code.

All paths below are inside `<run>/cli_metadata/work`; `E` means
`/offline_<normalized-run-id>`. Full argv is generated by
`cli_offline_common.command_plan()` and preserved with its actual interpreter
argv and command terminal marker. Each listed ID is from the existing manifest.

| Standard case | Actual operation and observable oracle |
| --- | --- |
| cli:pkg/create | Create mdds_offline_cpp with ament_cmake and mdds_offline_py with ament_python, probe_node entry points, explicit maintainer/license/dependencies. Parse package.xml, CMake/setup/source/resource files; no build or install. |
| cli:bag/list | Run storage, converter, compressor and decompressor, each plain and --verbose. Compare complete names/type/base/description against installed plugin XML; require sqlite3 and mcap ReadWrite interfaces and present AArch64 plugin libraries. |
| cli:security/create_keystore | Create work/keystore; verify CA self-signature/key public identity, both CA aliases, encrypted governance for domain 53 and its detached signature. |
| cli:security/create_enclave | Create E/alpha; verify leaf CN, CA chain/private-key public identity, complete artifacts, wildcard default permission topics, governance/permission signatures. |
| cli:security/create_key | Invoke the actual deprecated alias for E/beta and verify both enclaves and all new artifacts. |
| cli:security/create_permission | Regenerate E/alpha permissions from a fixed local policy: rt<E>/alpha/topic and rq/rr sum request/reply mapping, default DENY/domain 53/certificate validity/signature. |
| cli:security/generate_artifacts | Use a fresh work/generated_keystore, explicit E/extra identity and a policy containing E/gamma and E/delta. Verify all three identities, keys/certs and signed governance/permissions. |
| cli:security/list_enclaves | Require exactly E/alpha and E/beta from the primary scratch keystore. |
| cli:security/list_keys | Run the deprecated alias and require exactly the same two enclave identities. |

The board also captures all nine real `--help` invocations as separate
capability diagnostics; help is never included as a functional receipt
execution and cannot make a case pass. Missing Python libraries, plugin files,
CLI failures or capture failures remain visible failures. No live command is
silently approximated by an offline substitute.

## Public-artifact and signature proof

Keys are generated only in the owned work directories with umask 077. Private
key bytes never enter captures, logs or the archive. The board records only
algorithm, curve, mode and derived public-key digest for each private key;
the host checks those against the actual generated public certificates.
Resolved output links must stay inside the same generated keystore.

The board produces candidate captures, not PASS receipts. Its public JSON
contains exact file bytes and hashes for certificates, XML, detached p7s and
package scaffolding. The Windows host independently verifies X.509 signatures,
identity/key relationships, XML semantics and every detached signature with
the already-available `.pixi/envs/default/Library/bin/openssl.exe`.
OpenSSL uses -verify -text -binary and only the captured CAfile (no system CA
path/store). Binary output avoids Windows CRCRLF conversion while preserving
exact canonical XML content. Only public material is supplied to OpenSSL.

After successful replay, the host creates per-case functional receipts in a
new evidence directory. The observed board capture marker binds each raw CLI
execution to the hashed public artifact snapshot; separate host-oracle records
contain the real OpenSSL argv/exit/output and exact signed/unsigned/CA hashes.
Board stdout/stderr logs are copied byte-for-byte, never rewritten to invent
a board PASS marker. The original cli_acceptance validator then verifies the
new partial manifest: at most 9 PASS, all other 89 NOT_RUN, phase1=false and
gateway_unlocked=false. Neither previous 12-case metadata receipts nor the
standard 98-case template is rewritten or cumulatively marked passed.

These are file/metadata utility results. Generating DDS-security artifacts
does not prove MDDS enforces those permissions or uses DDS-security on the
wire, and this batch is not cross-board DSoftBus evidence.

## Host TDD

Initial plan/plugin/package/signature stubs produced 5 failing tests. Real
OpenSSL accepted the valid detached signature and rejected tampered content;
its positive test exposed the Windows text-output conversion and passed after
using -binary. A later signed-but-weakened governance test failed before the
topic-protection oracle was implemented. All 8 current tests pass, including
real certificate chains, key public-identity mismatch, changed policy data, and
nonzero CLI exits that cannot be converted into PASS receipts.
